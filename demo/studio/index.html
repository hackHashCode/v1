How PreCode-JEPA works

Idea: before a model writes code, it should know what that code will do. LLM-JEPA trains the model's reading of a task to predict an embedding of the reference code's text. PreCode swaps that target for an embedding of the reference code's behaviour: what it outputs when you run it.

h   = hidden state at the last prompt token (prompt only, same forward pass as SFT)
ẑ   = normalize(MLP(h))           MLP 1536 → 768 → 768, warmed up on frozen prompt states first
z   = frozen behaviour vector of the task's reference solution
loss = NTP(code) + 0.5 · InfoNCE(ẑ vs all 470 cached z, τ = 0.07)

The target. Each training task's reference solution runs in a sandbox on about 17 probe inputs: its test inputs plus edge cases (empty, negative, reversed, repeated…), one argument changed at a time. Exceptions count as behaviour. The trace lines f(args) -> output are feature-hashed into a 768-number vector. The function is renamed to f first, so the model can't "predict" behaviour by reading the function name.

Cost. h comes from the ordinary SFT forward pass (causal attention: it only sees the prompt), so training costs the same as SFT. The head is thrown away for inference.

At inference nothing changes. Code is generated exactly as with SFT. This studio additionally runs pred_head on the prompt state to show what PreCode "imagined", then executes every program to show what each one actually does.

Why the probe grid matters. Two programs can look almost identical and behave differently. The grid shows every program on the same inputs. With a reference solution, cells are marked right or wrong; without one, rows where the models disagree are highlighted.
